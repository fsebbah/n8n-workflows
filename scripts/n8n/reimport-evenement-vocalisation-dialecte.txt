# Deux workflows publient `vocalization_complete`, sur le MÊME stream, sous le MÊME nom :
#   · `Torah_Vocalization_Worker`         → `Préparer Fin Vocalisation`  (synchrone)
#   · `Torah_Vocalization_Batch_Callback` → `Préparer Événement`         (lot)
#
# Leurs jeux de champs avaient divergé sans que rien ne le signale. Un consommateur ne
# peut pas les distinguer à l'avance : il route sur `event`, identique dans les deux cas.
#
#   1. LOT, additif : `ok_count`, `fail_count`, `error_code` et `error_message` sont
#      AJOUTÉS, aux valeurs du synchrone. `enregistres` et `echecs` sont CONSERVÉS, donc
#      aucun lecteur existant ne casse. Sans ça, un écouteur écrit sur les noms du
#      synchrone — ce que le commentaire du worker lui recommande explicitement — lisait
#      `undefined` sur TOUT événement de lot : « 0 vocalisé » affiché, ou une exception.
#
#   2. SYNCHRONE : `correlation_id` devient CONDITIONNEL. Il était dans le littéral, donc
#      la clé partait toujours — avec la valeur `undefined` quand l'appelant n'en
#      fournissait pas. Or un champ de flux Redis doit être une CHAÎNE : un `undefined`
#      y devient le littéral « undefined », une valeur NON VIDE qui ressemble à un
#      identifiant et ne s'apparie à rien. C'est le chemin RÉELLEMENT EN SERVICE.
#
# ⚠️ Le correctif 2 touche le worker synchrone, celui qui tourne tous les jours (132 items
#    persistés le 2026-11-24). Le changement ne retire qu'une valeur parasite et n'ajoute
#    rien : aucun comportement de vocalisation ne change, seule l'émission Redis est plus
#    propre. Mais c'est un chemin vivant, donc le dry-run est à lire.
