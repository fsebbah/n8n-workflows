# Production tool sheet — how it is built, and what an empty cell means

Generated by `scripts/catalogue/generer_fiche_outils.py` → `fiche-outils-production.csv`.
**110 tools · 59 columns.** Schema agreed by Franck on 2026-11-10 (`azy.daily#642`).

## The rule that governs this file

**Every value is derived from the deployed workflow, or left empty. Nothing is guessed.**

An empty cell says "I don't know", and that is actionable. A cell filled on a hunch is a
trap — as Franck put it: *we displayed 91 credits for an actual 0.096 because someone
guessed the cost.*

**Source: the live `llm.local` instance, not the repository.** What clients are served is
what runs. The repo can diverge (measured 2026-11-10: 255 of 267 workflows identical).

All 110 tools in the production list are **active n8n webhooks** — verified 110/110 against
the 249 active paths on the instance.

## The four columns no team had listed

**`leaves_perimeter` is the best-filled of the four, and the most useful.** It is entirely
mechanical: the hosts called are in the code. **60 of 110 tools send data outside.**
Most frequent: OpenAI (23), Anthropic (16), Mistral (8), Google (12 distinct hosts),
Mathpix EU (2) — and one special case, **QuickChart**, the only one where the data leaves
**from the user's own machine** (`azy.daily#653`).

**`irreversible`** has three states: `yes` with the write operations named, `no` with its
reason, `to verify` when no outbound method can be determined. A POST to a **generation**
service (LLM, OCR, image) is **not** counted as irreversible: it is a cost, not a write to
the user's account. That says nothing about confidentiality — that is `leaves_perimeter`.

**`cost`** gives the unit (`per 1k tokens`, `page`, `call`, `character`) and the provider.
**No price**: n8n holds no rate card, and inventing one is precisely the mistake not to
repeat. Pricing belongs to chat.api.

**`input_limits`** carries only **literal** bounds found in the code (`max_files`,
`max_tokens`, `pages_max`, formats mentioned). 70 tools declare none — which does not mean
they accept anything, but that **nothing in the code bounds them**. That is itself a result.

## Precision columns (added after the first round)

- **`declared_enums`** — the allowed-value lists declared in code. This is the information
  that was missing: saying `entity-rating` accepts five entity types without naming them,
  or not saying `entity-social-actions` is restricted to **three named projects**
  (`bot-appetit`, `torah-bot`, `torah-fun`), makes a bounded tool look generic.
  **The absence of a list is information too**: `entity-list` validates only the
  *presence* of `entity_type`, never its value, where `entity-rating` restricts it to five.
  Two tools of the same family, two different contracts.
- **`required_inputs`** — the validation messages, **quoted verbatim from the code**, in
  whatever language that code uses. Translating them would misrepresent what the API
  actually returns to a caller.
- **`input_fields` / `output_keys`** — the observable input and output contract.
- **`endpoints_called`** — the exact endpoints, expressions neutralised, plus the custom
  node operations (`node op: event/create`). More precise than a hostname.

## Three measured traps — why they matter to you

**`estimated_time` is a CEILING.** It is the sum of the `timeout` values on the path.
`web-search` has a 243 s ceiling and may answer in 2 s. Execution retention is 37 h and
almost all of these tools are at **zero calls over 41 days**: there is **no distribution of
real durations to publish.** The ceiling bounds the risk honestly; presenting it as an
observed duration would be false.

**`result_kind` comes from the SERVICE, not the keys.** First version: `pdf-ocr` and
`audio-transcription` came out as `image` and `audio` — the opposite of what they return —
because `image_base64` and `audio_base64` are their **inputs**. Key names cannot tell input
from output; the endpoint tells you the direction of the transformation. An OCR turns an
image into text; image generation does the reverse.

**A custom node has no URL.** `mcp-gmail` came out as "no third-party host called" while it
talks to Google on every call, and `irreversible` was **empty** for a tool that can send and
delete mail. **Saying "no" where the answer is "yes" is far worse than leaving it empty.**
Three paths are now read: `*ToolDynamic` nodes, **native** integration nodes
(`n8n-nodes-base.openAi` for `text-to-speech`), and `https://` literals inside Code nodes.

Two false positives also removed: `url_tiers` now requires the **returned** URL to point at
the third party (not merely that the workflow calls one), and `example.com` is a
documentation placeholder. **A reader who finds one false positive stops believing the
column.**

## What this file cannot contain

- **`surfaces`** — 231 pending decisions. The registry publishes the field; it is filled on
  8 tools out of 239. Deriving it from a name would be deciding it in secret.
- **OAuth `scopes`** — the token arrives **already issued** by chat.api, which alone knows
  the scopes consented to. Guessing them would misrepresent what the tool can do.
- **`loses`** (what extraction discards) — requires comparing input and output on a real
  document. To be measured, not supposed.
- **`idempotent`** — requires replaying the same call and comparing.
- **`quota`, `usage_rights`** — governed by provider contracts.
- **`spoken_form`, `defer_to_history`** — the voice axis is an editorial decision, not a
  property of the code.

## And above all: 60 of 110 tools have no description

That is the number to look at before the other 58 columns. The script **fabricates no
prose**: an auto-generated description would look like documentation and would be approved
without being read. Front set the right test — *a tool whose description does not let you
decide when to use it should not be offered.*
